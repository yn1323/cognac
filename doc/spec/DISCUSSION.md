# ディスカッション仕様

タスク・探索で共通のマルチペルソナディスカッションの仕様。

## 目的

専門家チームがチャットアプリ上で話しているような、テンポの良いロールプレイ型ディスカッションを生成する。

## ペルソナ選定

### 人数

`config.discussion.minPersonas` 〜 `config.discussion.maxPersonas` 名（デフォルト 2〜4名）。

### tone 設定ガイドライン

各メンバーの tone は個性が際立つように具体的に設定する。以下のアーキタイプを参考に、チーム内でキャラが被らないようバランスを取る:

| アーキタイプ | 特徴 | 例 |
|:--|:--|:--|
| ツッコミ役 | 曖昧な方針に「それ本当に大丈夫？」と突っ込む | 甘い設計に容赦なく指摘 |
| 慎重派 | リスクやエッジケースを必ず指摘する心配性 | 壊れやすいポイントを見抜く |
| ムードメーカー | ノリが良くて「いいじゃん！」と盛り上げる | ポジティブに場を回す |
| 職人気質 | 技術的な美しさにこだわる完璧主義者 | 設計の一貫性を追求 |
| 現実主義者 | 「で、納期いつ？」とスケジュール感を気にする | 実現可能性を重視 |

## ディスカッションルール（共通）

以下のルールをタスク・探索の両方で適用する:

1. チャットアプリでの会話のように、短い発言（1〜3文）でテンポよくやり取りする
2. 1人が長々と話すのではなく、相手の発言にリアクションしながら会話を進める
3. 「それいいね」「なるほど〜」「ちょっと待って、それだと〜」のような自然な相槌・反応を入れる
4. 各メンバーは自分の専門領域の視点から発言する
5. 意見が割れるところは遠慮なく突っ込む（ただし建設的に）
6. 各メンバーの tone に設定されたキャラクター性を発言に反映する
7. 社内Slackみたいなノリで、絵文字をどんどん使ってOK！（😊🎉💡🤔👍🔥✨😅💪 など）
8. 発言の最初にリアクション絵文字を置いたり、文末に添えたり、自然に散りばめる
9. 長めの発言（2文以上）は途中で改行（`\n`）を入れて読みやすくする
10. 1ラウンドで合計 **8〜15メッセージ** 程度のやり取りをする

## 探索固有の追加ルール

探索ディスカッションでは、上記共通ルールに加えて以下の論点を含める:

- 何を調べるべきかを具体化する
- Playwright MCP を使うべきかを判断する
- 証跡として何を残すべきかを話し合う
- 最後は課題と次アクションの粒度まで揃える

## JSONフォーマット

```json
{
  "round": 1,
  "messages": [
    { "personaId": "ux-researcher", "content": "この画面、まずユーザーの導線から確認したいんだけど🤔" },
    { "personaId": "qa-engineer", "content": "💡 再現条件から先に切り分けない？\n環境差分がありそうな気がする" },
    { "personaId": "ux-researcher", "content": "たしかに！じゃあまず再現手順を整理しよう👍" }
  ],
  "shouldContinue": true,
  "reason": "まだ証跡の残し方について議論が必要"
}
```

## shouldContinue 判定基準

以下の場合は `false` にする:
- 全メンバーが主要な論点で合意に達した
- 新しい論点や反論が出なくなった
- 前ラウンドと実質的に同じ議論の繰り返しになった

## ラウンド制御

| ラウンド | ユーザープロンプト |
|:--|:--|
| 初回 | 「{対象}についてチャットで話し合って。各メンバーの初見の反応から始めて。」 |
| 続行 | 「この会話の続きをしてくれ。前の話を踏まえて、まだ決まっていない点を議論して。」 |
| 最終 | 「shouldContinueはfalseにして、結論を短くまとめるメッセージで締めてくれ。」 |

`{対象}` はタスクなら「タスク」、探索なら「探索依頼」。

## UI表示

ディスカッションの content フィールドは `whitespace-pre-wrap` でレンダリングされる。
プロンプト内の `\n` はそのまま改行として表示される。
